# Release notes

User-facing release notes, rendered in the app at **Account menu → Release notes**
(`/release-notes`). See "Release notes" in `AGENTS.md` for how to add an entry.

Format rules (the app parses this file, so keep to them):

- One `## <major.minor.patch> — <YYYY-MM-DD>` heading per release, newest first.
  The top entry is shown as the current version and must match `package.json`.
- Group bullets under `### Added`, `### Changed`, `### Fixed`, or a feature-area
  subheading. Plain markdown only.
- Every bullet gives the rationale: what changed, why (what was wrong or missing
  before), and what the reader will notice or should do now.
- Anything above the first `##` heading (this preamble) is not shown in the app.

## 2.9.0 — 2026-10-29

### Changed

- **Leaving Enforce only in these schemas blank now means syncing writes nothing.** Before, a blank list meant every schema of the managed catalogs. Clearing the field by mistake, or a saved value that failed to load, would quietly widen syncing from one schema to whole catalogs. Now enter `*` to sync every schema and the catalogs' own tags. With the field blank, syncing writes nothing and Sync history says why. Each entry is checked when you save, and one that isn't a `catalog.schema` name or pattern is refused. **If you sync whole catalogs today with this field blank, set it to `*`** under Admin → Settings → Metadata Manager, or syncing stops writing.
- **The removal safety limit now counts every removal in the last hour, and its default is 50.** Before, it counted each sync on its own, and saved changes were applied in batches of up to 200 tables. One bad import could therefore be spread over several syncs that each stayed under the limit. Replacing a tag's value with an empty one wasn't counted at all. The setting is now **Max removals per hour**: every tag removed or blanked and every description cleared counts, across all syncs in the last hour, and a sync that would go over writes nothing and pauses for review. A limit you set yourself is kept and now applies per hour.
- **Resuming a paused sync now applies only the removals that were reviewed.** Before, **Apply anyway and resume** ran a new full check with the limit switched off. Anything that had changed since the pause was written too, including removals nobody had looked at. **Review and resume** now offers **Apply these removals**, which re-checks only the paused sync's objects and writes them as long as that removes no more than the sync planned, and **Clear without applying**, which lifts the pause and writes nothing. Only Platform Admins can do either.
- **Editing an object that isn't managed yet now keeps the tags and description it already has in Unity Catalog.** Before, the first edit became the object's complete list. Once syncing was on, it quietly removed every tag you hadn't restated, and a bulk edit only warned about it. Now only what you change changes. Removing a tag, or replacing an object's tags, lists each removal in the preview, and removing a sensitive tag needs approval as usual. A first edit of up to 200 tables reads them from Unity Catalog again before saving, so a tag added since the last check isn't missed.
- **Undoing the change that started managing an object now stops managing it.** Before, the undo cleared the object's tags here, and syncing then removed them from Unity Catalog. That's the opposite of what someone undoing an import usually wants. Now Unity Catalog keeps the object's current tags and description, and the object goes back to not being managed. The preview marks it *Stops being managed* and warns about anything changed on it since.
- **Starting to manage objects now needs a recent read of Unity Catalog.** Start managing and imports copy the app's last full read, and syncing later removes anything that copy lacks. An old copy could therefore cost you tags added in the meantime. Both are now refused unless the catalog was read in full within the last 30 minutes, and the message tells you to choose **Check now** first. Admins can change the limit, or turn it off with 0, with **Freshest copy to start managing from** under Admin → Settings → Metadata Manager.
- **New tables are left alone until they've gone 10 minutes without changing.** Pipelines often create a table and tag it a moment later. A check that caught the table in between started managing it without those tags, and once syncing was on, the next check removed them as drift. Now a new or recreated table waits until it has been unchanged for **Wait after a new table changes** (10 minutes by default; 0 turns it off). A recreated table keeps the tags it was created with, alongside the ones saved here.
- **Full checks of large catalogs are faster.** A full check read a catalog's tables, columns and tags one after another, and re-read in pieces any catalog too big for one answer. A catalog of about 10,000 tables took around six minutes. These reads now run at the same time, and large results are downloaded directly from the workspace's storage. If the app can't reach that storage, it falls back to the old way for an hour, logs a warning, and still finishes, just more slowly.

### Fixed

- **A check that suddenly sees far fewer objects no longer marks them as dropped.** To a check, losing access to part of a catalog looks the same as a mass drop. Before, the missing tables were marked dropped, and once the retention period passed, their saved tags were deleted. Now a full check that would mark more than 5% of a catalog's objects as dropped (and more than 500 of them) saves nothing and shows the catalog as *Couldn't read*. If a large drop is real, raise **Max share missing per check**, choose **Check now**, then set it back. Saved tags for a dropped table are now deleted only after a later full check has read its catalog and still not found the table, and only while syncing is on.
- **A catalog that disappears, or that a re-check can no longer see, is reported instead of treated as empty.** When a catalog was dropped, renamed or hidden from the app, checks simply stopped reading it, and nothing said its list was out of date. Re-checking individual tables in a schema the app could no longer see marked those tables dropped. Now the catalog shows as *Couldn't read* with the reason, and a re-check leaves out a catalog or schema that stopped coming back instead of marking its tables dropped.
- **A check stopped partway through reading a catalog now marks that catalog unread.** Before, nothing recorded the cut-off read if the app restarted mid-read. The catalog looked as if it had been read successfully, and Start managing could copy an out-of-date read. Now the catalog shows *Couldn't read*, saying the last check stopped while reading it, until the next check reads it.
- **A sync now stops writing as soon as its settings change, the app shuts down, or another sync may have started.** Before, a sync that had started writing carried on to the end. That happened even if an admin had just set syncing to report only or narrowed the schemas, or a redeploy had begun. Now it checks before each batch of statements and stops, and Sync history says why. The next check writes whatever is still needed under the new settings. Settings saved on one copy of the app now also reach the copy running the sync.
- **One refused tag no longer blocks the rest of an object's changes.** Unity Catalog sets several tags in one statement, so a single refused value failed all of them, and any failure stopped the object's later statements. Now a refused statement is retried one tag at a time, and only problems with the object itself (it's gone, or the warehouse timed out) stop its other statements. If a view column's new value is refused after the old one was removed, the old value is put back. Tag keys longer than 255 characters and values longer than 1,000 are refused in the preview, since Unity Catalog would refuse them anyway.
- **A table that something keeps changing back is now retried less often.** When another tool or a pipeline kept resetting a table's tags, each reset brought the table straight back to be synced again, so the two fought over it every few minutes. Now a table written three times in an hour after changes in Unity Catalog is backed off, and its sync status says something keeps changing it back. Repeated changes no longer reset its retry count, and two edits of the same new table at once no longer collide.
- **Restating a tag an object already has no longer skips the permission check.** When a first edit of an object repeated a value Unity Catalog already had, that value was accepted without any permission check. An automation account could therefore start managing objects outside its scope just by restating their tags. Such values still need no approval, but the caller must now be allowed to change, or ask to change, that object. Otherwise the value is refused like any other edit.
- **The app no longer runs on an empty local database when Lakebase can't be reached.** If the app couldn't connect to Lakebase, it used a temporary local database. Everything looked empty, anything saved was lost at the next restart, and the safeguard that stops two copies of the app syncing at once did nothing. Now the app keeps trying Lakebase, and the health check reports the database as unavailable until it connects.
- **Sync history is now trimmed after 30 days.** Report-only checks list the same statements every hour, so Sync history grew without end and weighed on the app's database. Runs older than **Keep sync history** (30 days by default; 0 keeps everything) are now deleted a little at a time after each full check. Paused syncs, the newest run of each kind, and every change in History are kept.
- **A sync can no longer hang on the database or run the app out of memory.** Each database statement a sync runs now gives up after 15 minutes, and after one minute of waiting on a lock, instead of waiting indefinitely. A full check also holds no more catalogs in memory than it reads at once. It skips any catalog whose tables, columns or tags come to more than **Largest catalog read (rows)** (2,000,000 by default) and shows it as *Couldn't read*, instead of exhausting the app's memory.

## 2.8.1 — 2026-10-29

### Fixed

- **A Metadata Manager check cut off by a redeploy no longer shows as running for hours.** When the app was redeployed or restarted in the middle of a check, that check stayed *Running* in Sync history for up to six hours. Meanwhile **Preview a sync** and **Check and sync now** stayed greyed out, so you couldn't start a new check. Now the stopped check is marked *Failed*, with a note that the app restarted, as soon as Sync history loads, and you can start a new check straight away. Checks that are still working, including ones running in another copy of the app, are left alone.

### Changed

- **Sync history has one Check now button instead of Preview a sync and Check and sync now.** The two did the same thing while syncing was report only. Once syncing was on, the preview wasn't a safeguard either, because the hourly check and the checks that follow changes in Unity Catalog write without one. **Check now** does what the mode says: while syncing is report only, it lists what would be written, and once syncing is on it writes it, only in the schemas syncing is limited to. To see what syncing would do before it does anything, leave it on report only and read the checks it records. While syncing is off, the button is greyed out, because Unity Catalog isn't checked at all.

## 2.8.0 — 2026-10-29

### Added

- **Metadata Manager syncing can now be turned on for a single schema.** Before, enforce applied to every managed object in the catalogs it was given, so starting on one schema meant also writing every saved edit elsewhere in the catalog and removing tags people had added there directly. A new setting, **Enforce only in these schemas** (Admin → Settings → Metadata Manager), limits what enforce writes to the schemas you list. Everything else in the catalog is still checked and can still be edited, but stays as it is in Unity Catalog. In Sync history and on each table, statements and saved changes outside those schemas are marked *Report only*, and the removal safety limit counts only removals in the listed schemas. Leave the setting blank to keep enforcing whole catalogs, as before.

### Changed

- **Questions to Genie now go through Databricks' generally available Genie service.** The assistant was still calling the preview Genie endpoint, which Databricks switches off on November 30, 2026; after that date every data question would have failed. Answers, follow-ups and Genie details look the same as before. To ask Genie, you now need `EXECUTE` on `system.ai.genie_one_mcp` in Unity Catalog. Without it, the assistant says *Genie refused the request* and names the grant to ask your workspace admin for, where it used to show an unreadable connection error. Questions pinned to a single Genie space are unchanged.

## 2.7.1 — 2026-10-28

### Fixed

- **Previewing a Metadata Manager sync no longer freezes the page on a large catalog.** Choosing **Preview a sync** or **Check and sync now** used to wait until the whole catalog had been read from Unity Catalog before the page responded, so on a catalog with tens of thousands of tables the button stayed on *Previewing…*, the request often timed out, and the last check was recorded as unread. The check now starts in the background. The Sync history row shows *Running* and the page updates when it finishes; you can leave and come back. If a check is already running, the page says so instead of hanging.
- **When a catalog couldn’t be read, the page now says why.** The banner only said the last check couldn’t read the catalog, which left people wondering whether tags had been deleted. It now explains the usual causes (the warehouse ran out of time, the catalog is too large to read in one go, or the app doesn’t have permission to see it), and makes clear that the list still shows the last successful read. The failed check is under **Sync & admin → Sync history**.
- **Saving a tag while syncing is set to report only no longer looks as if Unity Catalog will update in a minute.** The table showed *Waiting to sync* and *Out of sync* for a tag that had only been saved here, which was easy to read as a failure. Those labels now say *Saved here only*, and the comparison explains that nothing is written until an admin turns syncing on.
- **Start managing catalogs no longer says every object is already managed when some aren’t.** The count of objects that would be newly saved used the same search as the total, so a catalog with leftover unmanaged tables showed “About 0 objects aren’t managed yet” and then saved them anyway. The count now excludes objects that already have a saved list, so the number matches what **Start managing** will do.
- **A check that couldn’t read a catalog no longer looks like a clean run in Sync history.** When Unity Catalog couldn’t be read (most often because the warehouse ran out of time on a large catalog), the check was still marked *Completed* with 0 objects checked, which looked like a quiet hour with nothing to do. The Sync history row now says *Couldn’t read* and names the catalog, and the sync’s details give the reason. Nothing in that catalog is changed by such a check, so it’s safe; it just means that hour’s comparison didn’t happen.
- **Start managing now refuses a catalog the last check couldn’t read.** Start managing copies the app’s last successful read of Unity Catalog, not a fresh one. If recent checks had failed, that copy could be hours old, and any tag added in Unity Catalog since then would be missing from what was saved; once syncing was on, the next successful check would have removed it. The dialog now explains this and waits until a check has read the catalog again. Objects you already started managing aren’t affected.
- **Sync history now says how much each check looked at.** Most rows re-check only a handful of objects, such as tables just created or altered in Unity Catalog, but they sat beside full checks of whole catalogs with the same columns. A small check showing 0 out of sync looked as if earlier problems had been fixed, when it simply hadn’t looked at them. Each row is now marked *full check* or *only these objects*. Checks started by a change in Unity Catalog say *Changed in Unity Catalog* instead of *After a change*, which read as if someone had edited something here.
- **A sync that has been running a long time can now be checked in the app’s logs.** Before, only the sync’s last line mentioned its id, so there was no way to tell a slow sync from a stuck one while it ran. Every line a sync writes now includes its id (shown at the top of its details), each catalog logs when its read starts, and a read the warehouse is still working on logs a line every minute. If new lines keep appearing, it’s working. Each warehouse read is canceled after about five minutes, so a sync never waits on Unity Catalog indefinitely.
- **Full checks of a large catalog finish sooner.** Every full check used to save its whole copy of the catalog again, every table and column, even when almost nothing had changed in Unity Catalog. On a catalog with hundreds of thousands of objects, that saving alone could take ten minutes or more, and edits made here waited for it to finish before syncing. A full check now saves only the objects that changed, appeared or disappeared since the last one. Nothing else changes: an object’s *Last checked* time still moves with every check that reads it, and the app’s logs now say, for each catalog, how many objects changed and how long saving took.

## 2.7.0 — 2026-10-28

### Added

- **The app log now follows a person through a session.** Before, the log showed which API calls were made but not which screens someone was on, nothing that broke in their browser, and not their app roles, so watching a user-testing session or chasing a bug report meant guessing. Now each page someone opens and each error their browser hits is written to the app's own log, every line carries their email and app roles (including a role simulated with Dev persona mode), each chat turn gets one line saying which tools it used, how long it took and whether it ended in an error, and every request records how long it took. Nothing is sent outside the app, and no page content, chat text or query results are logged. To stop the browser reporting page views and errors, turn off **Log page views and browser errors** under **Admin → Settings → Infrastructure → Logging**.
- **Bug reports now name the server's log lines for each failed call.** Every response carries a request ID, and a bug report with diagnostics attached keeps it next to each failed network call. Admins see it on the report under **Admin → Feedback** and can search the log for it, instead of matching reports to log lines by time.

### Changed

- **OmniGuard scans log a summary instead of every check.** A scan wrote one line for every policy check and every violation, tens of thousands of lines a run, which buried everything else in the log. It now writes one line per workspace with the number of checks and violations by policy, and one line for the whole run. Every check and violation is still recorded on the run itself, so nothing is lost from the OmniGuard pages.

## 2.6.4 — 2026-10-28

### Fixed

- **The assistant now knows where admins read feedback, and no longer files a question as feedback.** A Platform Admin who asked where to see submitted feature requests was told there was no such page, and the assistant then offered to log a request to build one, even though **Admin → Feedback** already does this. Earlier in the same chat, a plain question ("how do you capture user feedback?") had been filed as feedback. The assistant now sends Platform Admins and Governance Admins to **Admin → Feedback**, tells everyone else that the admins review what is sent (without linking a page they can't open), and answers questions about how feedback works instead of filing them. It stays quiet about the page in environments where an admin has turned the Feedback page off. It still can't read what has been sent, so it won't describe the contents or status of a report.

## 2.6.3 — 2026-10-28

### Fixed

- **Simulating a role no longer hides the Metadata Manager.** In environments that allow **Dev persona mode** (the toggle in the account menu that lets you view the app as another role), switching to a role such as Platform Admin showed you the rest of the app as that role, but the Metadata Manager still treated you as your real role. The sidebar link stayed hidden, and opening the page directly said you can't browse metadata, so it could not be tested as an admin. The Metadata Manager now follows the simulated role like every other page. This affects only environments where Dev persona mode is available; it stays off elsewhere, and people there see their real roles as before.

## 2.6.2 — 2026-10-27

### Fixed

- **Asking for a dashboard now gets the next step straight away.** The assistant searched the catalog first and then asked which dataset to use, so you waited and read a question before learning that dashboards are built in Databricks, not in the chat. It now tells you right away that this happens in **Dashboards** in your workspace, says what to do there, and then offers to help you find data to build it on.
- **When several tables share a name, the assistant asks which one you mean instead of answering for one.** Asked who owns "the shipments table" when 29 assets matched, it said so, then gave the owner of one of them anyway, which could have sent you to the wrong person. It now lists a few of the matches and asks you to pick before it looks up an owner, your access or any other detail.
- **If you can't use the Metadata Manager, a correction to a description or tag is now routed to someone who can make it.** The Metadata Manager is limited to governance and data owners, and when a business user asked for a wrong description to be changed the assistant stopped at an access error and suggested asking an admin to change roles, which was no help. It now says that only the table's owner or governance can change it, names the owner, and offers to draft the request to them (or to report the problem, where feedback is switched on).
- **Workflow test runs no longer present a simulated action as a failure.** In a test run, actions that would change something are simulated rather than carried out, and the assistant sometimes read that as an error and told the tester the request "didn't go through". The simulated result now says plainly that it should be treated as having succeeded, so a test run reads the way a real one would.

## 2.6.1 — 2026-10-27

### Changed

- **The assistant answers training and community questions from what is actually switched on.** It used to carry its own copy of the course list and the community links, which had drifted from the Training page and from the links an admin had set up, so it could recommend a course that no longer existed or send you to a page that was turned off. It now looks up the courses on **Training** and the links on **Community Links** as they stand when you ask, points you to the right page, and says plainly when there is nothing to recommend instead of naming something from memory. It only mentions a page while that page is on in **Admin → Settings**, so turning a page off stops the recommendations on the next message.
- **The assistant sends you to View & Search Catalog when you want to look around yourself.** Asked whether there was a page to browse and search for tables, it pointed you to the catalog in Databricks because it didn't know the app has one. It now links **View & Search Catalog** (while that page is on) and still offers to search for you.
- **The assistant's standing instructions are about 30% shorter.** Every message used to re-send a list of all the assistant's tools, which the model already receives separately, plus a full copy of the training and community content. That extra text made the model's input bigger on every message, which slows replies and uses up the model's per-minute allowance faster when many people chat at once. Its behavior is otherwise unchanged except for the fixes below.

### Fixed

- **Answers from Genie now include the data and keep their context in follow-ups.** For general Genie questions the chat showed only the written answer, because the rows behind it were never fetched, so there was no table to open and nothing to chart. A question that Genie stopped partway through (it reports this as "incomplete") also left the chat waiting until it gave up. Now the table appears and can be charted, an incomplete answer is shown with whatever Genie produced (or a plain message if it produced nothing), and a follow-up such as "now by region" continues the same Genie conversation instead of starting over. Genie is slow, so the assistant now reaches for it only when a faster lookup, or a query on a table it already knows, won't do. This applies only where an admin has turned on **Ask your data**.
- **A Genie follow-up no longer fails with "not found" when you ask it straight after the first answer.** Now and then Genie reports a question it has only just started on as missing, for a moment, and the chat treated that as a failure and showed an error even though the answer was ready a second later. The chat now keeps waiting for up to thirty seconds when Genie says this, so the answer appears as normal; if Genie still cannot find it after that, you see the error as before. This applies only where an admin has turned on **Ask your data**.
- **Hand-offs to your Databricks workspace no longer start with research or claim a fix is verified.** The rule for pointing you to the SQL editor or Dashboards told the assistant not to run lookups, and then told it to include columns it had checked and whether you have access, so it ran lookups anyway, sometimes ran your query, and then described a guessed column name as confirmed. The instructions no longer contradict each other: the assistant is now told to answer straight away with the full table name you gave, to say that a corrected query is a likely fix it hasn't run, and for a dashboard to give the next step first and then offer to help choose data. It follows this most of the time but not always, so when you paste a broken query it may still look the table up before answering.
- **The assistant stops retrying a lookup that was refused or came back empty.** Asked about a table you can't read, it could try five or six variations of the same check before answering. It now says what it could and couldn't check and offers the next step. For quality, SLA and freshness questions it reports what is recorded (or that nothing is) and names the owner as the person who can say more, rather than running its own checks.
- **Table names are quoted as found, and ambiguous names list every match.** The assistant occasionally rebuilt a table's full name from memory, giving a catalog the search never returned, and, for a bare name such as `shipments`, named two candidates as if there were only two. It now quotes names exactly as returned, says how many tables matched, lists the first few and asks which you mean. When asked which groups hold access to something that nothing matches, it says plainly that no group is recorded as holding it.

## 2.6.0 — 2026-10-27

### Added

- **Admins can set a day-to-day support contact, and people can find it.** There was nowhere to say who handles everyday help, so a user who asked "who do I contact?" got no useful answer, and the Team & Support tab in Discover only showed contacts that a dataset's own contract happened to list. A Platform Admin can now enter a name, email, and hours or channel under **Admin → Settings → Links & Embedded Apps → Support contact**. The contact appears on the **Team & Support** tab of every asset in Discover, and the assistant gives it when someone asks who to contact. Until an admin fills it in, nothing is shown and the assistant doesn't guess.

- **The assistant can tell you about a single table, including its columns and how fresh it is.** Asking about a table used to return only a description and owner, so questions about its columns, quality or last update had no answer. The assistant now combines the catalog (description, owner, tags, certification, data quality results and refresh promise when recorded) with a live look at the table as you, which adds its columns, types and comments and when its definition last changed. It is explicit that this isn't the same as when the data was last refreshed, and checks the table's history or quotes the refresh promise when you ask about freshness. Nothing is made up: if no quality result or refresh promise is recorded, it says so.
- **"Do I have access?" and "What can I access?" now get a real answer.** The assistant could list who holds access to something, but not whether you did, so you were left to work it out from group names. It now compares the access rules with your own groups, tells you which of your groups holds the access, or that none is recorded, and offers to help you join one or request access. The recorded rules don't include every grant, so when none of your groups holds the access the assistant settles it straight away by trying a one-row read of the table as you, instead of asking whether you'd like it to. It says you have access only if that read works, says you don't only if Databricks refuses it, and says it couldn't check if something else went wrong. When you ask for access for yourself, it no longer picks a group for you: it asks which one you mean, and if a group already holds the access it tells you to join it rather than preparing a request that would change nothing. When you ask whether you can read and write a table, it answers each half separately: read from the check, and write from your groups' access rules. It never tests write access by writing, so with no matching rule it says it can't confirm write access and that the owner can, rather than telling you that you can't write.
- **The assistant now hands off queries, dashboards and table changes instead of improvising.** Asked to write a query to keep, build a dashboard or change a table's data, it used to try, and the result couldn't be saved or run where you work. It now says this happens in your Databricks workspace, points you to the SQL editor, Dashboards or Genie Code using the names your organization uses, and takes along what you will need there: the full table name, its columns, its owner and whether you have access. For a table or data change it points you to the owner and can draft the request. Questions answered with data, and tag or description changes, work as before.

### Changed

- **You can tell the assistant about a problem with data without choosing a category.** The assistant's feedback route was described as being about this app, and it wanted every report labelled as a bug, a feature or feedback, so a report like "the shipments table hasn't updated since Friday" could feel like it didn't belong. The assistant now accepts any report, picks the label itself, never asks you to classify it, and records which table or dashboard you mean so admins can see it at a glance. It won't promise a fix, and offers to look up the data's owner so you can also reach out directly.

- **The Metadata Manager now says the same thing everywhere about when your changes are saved.** The welcome card said "Nothing is saved yet", the table page said changes were "saved as soon as you review them", and the result said they were "queued for Unity Catalog" even when syncing was set to report only. Together those left it unclear whether a change was live. Edits now wait at the bottom of the page until you select **Review and save**, and the result states plainly whether the change will reach Unity Catalog soon or is only recorded here because syncing is off or set to report only.
- **The Metadata Manager's header link for admins is now called Sync & admin.** The page header and the sidebar both had a link called **Admin**, and the header one opens a different page (sync status, objects out of sync, sync history, automation access and bulk onboarding) from the platform dashboard that the sidebar one opens. The page header link and the Guide use the new name; the sidebar link is unchanged.

### Fixed

- **Queries the assistant runs for you no longer come back empty.** Databricks began returning query results in a newer format that the assistant didn't read, so a query that succeeded could show no rows and be marked as cut off. You saw this as the assistant saying a table's history had no entries, or being unable to say when data last changed. Results now show their rows, and a question like "how fresh is this table?" gets the date of the latest change.
- **Searching for a table by its full name now finds that table.** The assistant could answer "who owns `catalog.schema.table`?" but, asked to search the catalog for the same name, show other tables that merely shared a word with it. Searches matched thousands of tables, but only an arbitrary 200 of them were ranked, so the exact table could be left out before ranking began; the larger the catalog, the more often that happened. Results are now ranked before they are cut, a table named in full always comes first, and the match count shows the true total instead of stopping at 200.
- **"What groups am I in?" now answers from your Databricks groups.** The assistant looked in the corporate directory, which isn't connected everywhere, and could tell you that you belong to no groups when it simply couldn't see them. It now reads your Databricks groups, and when a directory isn't connected it says it can't see those memberships instead of saying you have none.
- **The assistant files a data problem only when you ask, and only once.** Describing a problem, such as "this table looks stale", was enough for it to send a report to the admins without asking, and saying "yes, report it" afterwards sent the same report again. It now looks up the owner, tells you what it found and offers to report it, and waits for your yes. If you or the assistant repeat a report within fifteen minutes it is recorded once, and the assistant says it is already with the team.
- **Hand-offs to your Databricks workspace are shorter and cleaner.** When it sends you to the SQL editor, Dashboards or Genie Code, the assistant used to run several lookups first and could mention a token or connection error that had nothing to do with your question. It now leads with where to go, links the SQL editor, answers "is this table in a dashboard?" from the catalog, and says plainly when your organization hasn't set up a support contact or defined a term such as "steward" instead of searching for one.

A separate deployment setting prepares chosen app tables for Lakebase Change Data Feed, so requests, approvals, the enforcement audit and access-rule history can be copied into Unity Catalog. Both are off until an operator turns them on, and the platform setup guide walks through each one.

### Changed

- **Access rules use an allow list of privileges.** The never-granted list only blocked the privileges named on it, so anything else could be requested, including privileges Databricks adds later. Now a request or a direct edit can add only the privileges a Platform Admin lists for each securable type under **Admin → Settings → Access Rules → Allowed privileges**. The starting list is every privilege that was allowed before, so nothing changes until you edit it, and a new privilege can't be granted until someone adds it. Existing rules stay as they are and removing access is always allowed; if you had customised the never-granted list, check the new allow list, because that customisation isn't carried over.
- **The access-rule approval step names its approver group.** The approval card and the workflow editor used to say only "Platform Admin", which suggested no group was involved even when one was set. The card now says which group approves, for example "UC securables approvers: grp_data_stewards", or "Platform Admins (no UC securables group set)" when that type has no group, and the requester's own request page says the same. The step is labelled **Access rule approvers** in the request's timeline and in the workflow editor, which also lists the three groups with a link to their settings, and the card no longer repeats the prepared change as raw data, since its report already shows it. Who can approve hasn't changed.
- **Access-rule requests now go through Prepare, Approve and Record.** The steps used to be called Plan and Apply, which was easy to confuse with Terraform, although nothing reaches Terraform at these steps. Prepare works out the exact rule changes and who approves them; Record writes the approved change into the access rules, and the next export carries it to Terraform. Requests already in progress finish normally.

### Fixed

- **Import findings give the row number you see in Excel.** Findings counted from the first data row and skipped blank rows, so every number was at least one short of the row in the workbook. They now count the header as row 1 and include blank rows, so you can go straight to the row they name.
- **Account groups work as approver groups.** An approver group that exists in your Databricks account but isn't assigned to this workspace, as Unity Catalog groups often aren't, showed as "Not found in Databricks". Its members also weren't recognised, so they couldn't approve or edit that type, and the warning that approvals only reached Platform Admins was right. Now such a group shows **Found in the account**, and the app reads each person's account groups when they sign in, so members get the approvals and edit rights. A group mapped to an app role under role mappings now applies to its members in the same way, even when it isn't assigned to the workspace. "Not found" now means no group in the workspace or the account has that name.

## 1.0.0 — 2026-09-30

The first stable release. It brings a conversational agent, governed requests and
approvals, data discovery, governance tooling, and no-code building blocks together
in one place.

### Agent and requests

- Ask the agent in plain language to find data, answer questions about your data, or request access and resources. Before it changes anything, it shows you its plan and asks you to confirm.
- Answers about your data appear directly in the chat, with tables and charts rendered inline, and your conversations are saved so you can pick up where you left off.
- Every request is tracked under **My Requests**, with its live status, step-by-step progress, and a full history of what was done on your behalf.
- Long-running work continues in the background and resumes safely after an interruption, so a request is never applied twice.

### Discover and analyze

- Browse business domains, search the catalog, discover metric views, and explore data lineage from the **Discover** page.
- Every domain, subdomain, and asset on **Discover** has its own link. Use **Copy link** to share exactly what you're looking at, and anyone who opens it lands on the same view.
- **Reports** lets you manage recurring reports that the agent generates automatically.

### Approvals

- Higher-impact changes, such as granting access or creating infrastructure, are routed to the right approvers before they run.
- Approvers work from **Pending Approvals**, where each approval card includes a summary of the work completed so far, and can set up out-of-office delegations so nothing stalls while they are away.

### Governance

- Every action the agent takes is checked against policy and recorded in an audit trail, and the agent never has more access to data than the person asking.
- **OmniGuard** scans workspaces for policy violations and reports findings you can act on, while the **Allowlist** records approved exceptions it should leave alone.
- **Data Certification (ODCS)** tracks which datasets meet your standards for quality, documentation, access control, and classification.
- **Data Products (ODPS)** catalogs your logical data products and their contracts, and **Tag Management** keeps governance tags on data assets consistent.
- The **Context Catalog** holds the house rules and reference material the agent reads, so it steers people toward compliant choices before a request reaches an approver.

### Build and customize

- **Workflow Studio** lets administrators design request workflows visually, choosing the instructions, allowed actions, and approval rules without writing code.
- The **Tool Registry** shows every action that workflows and the agent are allowed to take, and who each one is available to.
- **Training Studio** is where administrators author learning tracks and courses, upload media, and see how the content is being used.

### Learn and share

- **Training** offers structured learning paths, and the **Event Calendar** lists upcoming sessions.
- **Templates & Assets** is a shared library of design patterns, templates, and reusable components, and **Community Links** collects the resources and tools your organization recommends.

### Administration

- Administrators can change the app's name, logo, colors, and enabled features, and adjust runtime settings live from **Admin → Settings** without a redeploy.
- Anyone can send feedback or clear their saved data from the account menu, and this **Release notes** page shows what has changed in each version.
